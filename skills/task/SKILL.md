# Task

Manage an explicit task lifecycle without forcing every phase at once. Reuse verified resources and complete only what is missing.

## Configuration

Read the task-skill environment before changing any task state. The installation
guide defines every variable and the matching cc-connect/Codex settings. The
required runtime values are:

- `CC_CONNECT_TASK_WORKSPACE_ROOT` (defaults to `~/workspace`)
- `CC_CONNECT_TASK_DATA_DIR` (defaults to `~/.cc-connect/data`)
- `CC_CONNECT_TASK_PROJECT` (defaults to `workspace`)
- `CC_CONNECT_TASK_LARK_CLI_BOT_APP_ID`
- `CC_CONNECT_TASK_USER_OPEN_ID` (the current user ID visible to the lark-cli Bot app)
- `CC_CONNECT_TASK_BOT_APP_ID`

Task documents are organization policy, not a built-in assumption. A comma-separated
`CC_CONNECT_TASK_DOCUMENT_REMOTE_HOSTS` enables them for repositories whose configured
Git remote host matches exactly. When enabled, also require
`CC_CONNECT_TASK_DOCUMENT_FOLDER_URL` and
`CC_CONNECT_TASK_DOCUMENT_FOLDER_TOKEN`. Store documents directly in that folder;
never create per-repository subfolders. An empty remote-host list disables task
documents everywhere.

Lark user open IDs are app-scoped. Do not assume
`CC_CONNECT_TASK_USER_OPEN_ID` is the same ID that cc-connect's Feishu Bot returns
from `/whoami`; use each app's own verified user ID in its configuration.

Create groups with the configured lark-cli Bot identity. Never use that Bot to send lifecycle controls, task prompts, ordinary prose, status updates, task-document links, summaries, or results: cc-connect accepts this Bot as an inbound sender and can otherwise treat those messages as user turns. Route, attach, status, and unbind use cc-connect's local Unix-socket CLI only; no Feishu message is an automation control plane.

Send every ordinary task-group message through the running cc-connect instance as the cc-connect Bot, using its local outbound interface and the exact group session key:

```text
cc-connect send --project "$CC_CONNECT_TASK_PROJECT" --session 'feishu:<chat-id>' --data-dir "$CC_CONNECT_TASK_DATA_DIR" --message '<message>'
```

`cc-connect send` has no idempotency key: for a once-only lifecycle notification, use stable exact text, inspect complete group history before sending, verify the sent message and sender afterward, and inspect history rather than retrying after an uncertain result. When the task document policy is enabled, form a task-record notification by concatenating the literal prefix `Task record: ` with the exact bare document URL and putting nothing after the URL on that line. Never wrap it as `<url|title>`, use another labeled-link syntax, or append the document title to the URL; if a title is needed elsewhere, place it on a separate line. Create and update applicable task documents and manage the current user's Feed Shortcut with user identity. Before a Feishu operation not already encapsulated by the lifecycle script, load the applicable installed `lark-im`, `lark-doc`, or `lark-drive` skill and its prerequisites; do not duplicate or guess its API details here.

Read `~/.codex/AGENTS.local.md`, the global `AGENTS.md`, and applicable project instructions before changing project or task state.

## Invocation

Codex runs the global `UserPromptSubmit` hook before the Agent receives an explicit
execute or finish prompt. For every complete transition prompt, the hook idempotently
switches the persistent native thread to Default and supplies the Default-mode
developer context for that same turn. It accepts the same direct `$task` command
from native Codex or cc-connect, plus the exact task-skill envelope generated by
cc-connect's legacy `/task` alias. It must not infer collaboration mode from the
hook event's `permission_mode`, which Codex derives from approval policy. This keeps
the primary mode transition in the Task bundle rather than in a cc-connect-specific
Task implementation. Read
[references/mode-hook.md](references/mode-hook.md) when installing, testing, or
diagnosing this hook.

Supported manual primitives are:

```text
$task init [task prompt]
$task exe[cute]
$task fin[ish]
```

Use the same `$task ...` form through cc-connect and Feishu. For `execute` and
`finish`, accept any unique ASCII prefix of at least three letters and normalize it
to the canonical primitive: `exe` through `execute`, or `fin` through `finish`.
Matching is case-insensitive, but the complete direct message must contain only the
transition command and surrounding whitespace; extra arguments or prose do not
trigger a mode change. Do not abbreviate `init`, and do not treat the shorter
reserved prefixes `e`, `ex`, `f`, or `fi` as init prompts. Treat other
`$task <task prompt>` forms without a primitive as `init <task prompt>` for
compatibility. cc-connect's legacy `/task ...` skill alias remains accepted for
existing clients, but new instructions and automation must use `$task ...`. Never
invoke this skill implicitly for an ordinary task request.

Use `~/.agents/skills/task/scripts/task-lifecycle-control` for deterministic task orchestration. Every command re-discovers current state from Git, Codex, Lark, and cc-connect and returns one verified JSON result. It must not create, read, or require a lifecycle state/log file. Read [references/init.md](references/init.md) for the init contract.

Use `~/.agents/skills/task/scripts/codex-task-control` only for lower-level native thread lifecycle controls used by the orchestrator and final archival. It talks directly to the local Codex App Server and does not route commands through Feishu or cc-connect. Pass the verified native thread ID explicitly and require the helper's successful, verified result before continuing:

```text
codex-task-control --thread <id> --json plan
codex-task-control --thread <id> --json default
codex-task-control --thread <id> --json queue '<exact prompt>'
codex-task-control --thread <id> --json archive
codex-task-control --json ensure-thread --cwd <absolute-cwd> --name <exact-name>
codex-task-control --json list-threads --cwd <absolute-cwd>
codex-task-control --thread <id> --json inspect
```

Direct `plan` and `default` calls change only subsequent turns. The global prompt
hook is the normal Task path that pairs a verified persistent Default update with
developer context for the prompt already being submitted. `queue` uses Codex's
native follow-up queue and remains available for compatibility and recovery; do not
use it for the normal execute or finish transition. `archive` archives an idle
thread immediately; for an active thread, it starts a detached watcher that waits
for the current turn to become idle and then archives it. An immediate result must
report `archived: true` and `verified: true`. A deferred result must report
`scheduled: true`, `archived: false`, `verified: true`, and a `stateFile`; in that
result, verification applies to the durable schedule, not to completed archival.
Never send `/plan` or `/archive` as prompt text, and never claim success from the
helper's exit status alone when its JSON result is missing or unverified.

Task-worktree finish never commits, merges, rebases, or pushes task changes. Before
cleanup it requires the task branch's committed changes to be present in the stable
default branch. It checks the local stable HEAD first; only when that check fails
does it fetch the remote default and safely fast-forward the stable checkout,
preserving non-conflicting local state. If the refreshed default branch still lacks
the task changes, finish stops before unbinding or removing the worktree.
Stable-checkout finish has no task branch or integration gate and never updates or
removes the stable checkout.

Compatibility diagnostic: the `plan` and `default` handoff relies on the experimental App Server collaboration-mode path, including `collaborationMode/list` and `thread/settings/update`. The current compatibility baseline is Codex/App Server `0.152.x`; the deployment used to synchronize this bundle runs `0.152.1`. A successful update request is the protocol acknowledgement; when the server emits `thread/settings/updated`, the helper additionally validates it. A repeated no-op update may legitimately omit that notification. After a Codex upgrade, treat an unknown method, a missing `plan` or `default` preset, or rejected collaboration-mode fields as likely protocol drift before investigating cc-connect, task identity, or prompt delivery. Compare the running CLI and daemon versions, inspect the generated version-matched App Server schema, and confirm that initialization still enables `experimentalApi`; update and revalidate the helper before queueing a task prompt. Do not fall back to sending `/plan` as prompt text.

The intended automated sequence is:

```text
$task init -> Direct/Contextual: Plan-mode queued turn | Deferred: next user turn in Plan mode -> plan review -> $task execute -> pre-turn hook selects Default -> implementation -> acceptance -> commit and integrate -> $task finish -> pre-turn hook selects Default when needed -> native archive after the final turn
```

Each primitive is independently invocable and reconciles live resources. Init and
execute do not require a recorded lifecycle phase; task-worktree finish additionally
enforces the clean-worktree and main-integration safety gates above. Stop on a
current source-of-truth ambiguity, an exact-identity conflict, missing applicable
integration, or an operation that could lose uncommitted work.

## Task document policy

After project discovery, inspect the configured Git fetch remote URLs of every verified repository in the task. Enable the task document when at least one remote host exactly matches an entry in `CC_CONNECT_TASK_DOCUMENT_REMOTE_HOSTS`; support ordinary HTTPS/SSH URLs and scp-like Git syntax such as `git@git.example.com:org/repo.git`. Match the parsed host exactly, not a substring or directory name. This is a local Git-metadata check and does not require contacting the remote.

When no verified repository matches a configured document remote, the disabled policy overrides every task-document instruction in this file and its references:

- Do not search for, resolve, create, import, update, or share a Feishu task document.
- Do not send a `Task record: ` notification and do not load `lark-doc` or `lark-drive` solely for task-document work.
- Treat the missing document, URL, and notification as expected and not applicable; they must not block `execute`, implementation, `finish`, cleanup, or archival.
- Report the task document as `not applicable (no configured document remote)` in lifecycle results.

Repositories with no remote, only local-path remotes, or other non-matching hosts do not use a task document. For a cross-repository task, one verified matching repository enables the shared task document.

## Task identity

A verified Git branch or worktree is authoritative. Otherwise infer the project and a concise goal from the prompt and current thread. For a new Git task derive:

```text
branch       = ws/<angular-type>/<lowercase-hyphen-slug>
worktree     = <workspace>/<repo>/worktrees/ws_<angular-type>_<slug>
group_name   = <repo>-<slug>
group_description = <native thread ID>
thread_name  = <branch>
task_name    = <branch>
document     = <YYYY-MM-DD> <task_name> | not applicable when policy is disabled
```

Use the exact checked-out branch, including `ws/`, for an existing Git task's thread and `task_name`. For a deliberate non-Git task, use one concise, specific English name for both. Do not treat failed Git discovery as a non-Git task.

When the task document policy is enabled and a document is first created, prefix `task_name` with that creation date in zero-padded ISO form, for example `2026-08-27 ws/feat/foo`. Keep that title unchanged during later updates so the task remains sorted by creation date.

When the task document policy is enabled, resolve an existing task document in this order: a verified URL/token already recorded in the current thread, the link previously sent to the eligible task group, then a unique document directly in dev-notes whose title matches `YYYY-MM-DD <task_name>`. Reuse a verified legacy unprefixed document instead of duplicating it. Never guess among multiple matches or create a duplicate after an uncertain write.

## `init`

Read and follow [references/init.md](references/init.md). After resolving the agent-owned decisions, invoke `task-lifecycle-control init` once. Do not reproduce its Git, Codex, Lark, or cc-connect steps manually. Explicit `init` authorizes the standard non-destructive reconciliation writes encapsulated by that command without another confirmation.

Classify the input as `Direct`, `Contextual`, or `Deferred` before changing task state. Preserve the user's original request for provenance, but remove only unambiguous task-lifecycle wording from the request sent to the already-created target thread. A `Contextual` init also authorizes creation of the verified lifecycle-owned `handoff.md` at the target worktree root as defined in [references/init.md](references/init.md). The expected untracked file is the task's first local change and requirement record, not the Feishu task document; never stage or commit it.

Do not create the task document during `init`. Require the command's `ok: true`, `verified: true`, exact resource identities, verified Plan result, and mode-appropriate queue result. Direct queues the exact effective request; Contextual materializes/verifies the handoff and queues its immutable path/digest reference; Deferred leaves the native queue untouched. Do not replay any payload through Feishu or start planning in the invoking turn.

If Plan mode was verified but prompt queueing is uncertain, preserve the exact computed `queue_payload` and stop; inspect the native queue before any retry. Do not regenerate a contextual handoff or its reference prompt during recovery because byte changes would defeat exact-message idempotency.

## `execute`

Explicit `execute` means the latest reviewed plan in the task thread is approved and authorizes the applicable document creation/update and group notification, plus implementation. Do not ask for another routine confirmation. If there is no settled plan, the task identity is ambiguous, the selected thread/worktree conflicts, or the host is still preventing writes in Plan mode, stop with the precise missing action.

An explicit execute prompt submitted while the thread was in Plan mode must arrive
with the global hook's verified Default-mode developer context. Treat that context
as authorization to continue in the same turn and do not call
`task-lifecycle-control execute`, run another mode handoff, or queue a duplicate
`$task execute`. If the prompt still arrives under Plan instructions, the hook did
not run successfully: stop and report the hook installation, trust, App Server
control, or prompt-recognition failure. Do not ask the Plan-mode Agent to repair its
own mode.

Before implementation:

1. Reconcile any missing initialization resources using [references/init.md](references/init.md).
2. When the task document policy is enabled, resolve the existing task document. If none exists, create it as the current user directly under the configured dev-notes folder using its parent token and the dated title rule above. If it exists, update it instead of creating another.
3. When the task document policy is enabled, record the task goal, relevant project/branch/worktree/thread/group metadata, the approved plan, acceptance criteria, and material risks or constraints. Keep the document concise and use the applicable `lark-doc` writing guidance.
4. When the task document policy is enabled, ensure the eligible task group contains the canonical notification formed from `Task record: ` followed immediately by the exact bare document URL, with no trailing title or link wrapper. Search complete group history for the exact document token or URL and, only when absent, send the notification through cc-connect's local outbound interface. Verify the message, clickable URL, and cc-connect Bot sender afterward; after an uncertain send, inspect history before retrying. Never send this notification with the lark-cli Bot.
5. Verify the applicable policy gate: either the document location and notification are verified, or verified remote metadata proves that no repository matches the configured document hosts. Then implement the approved plan in the selected native task thread. If the suitable current thread is selected, continue there directly rather than creating or messaging another thread.

When the task document policy is enabled, the plan document is a gate: if it cannot be created or updated and delivered to the task group, do not begin implementation. Inspect state before retrying an uncertain write. When the policy is disabled, do not attempt this gate.

## `finish`

Explicit `finish` means the user wants to end the workspace/thread now; it does not assert that any workflow phase is complete.

Classify the finish target from the invoking native thread's exact cwd:

- Use task-worktree mode, `--branch <exact-ws-branch>`, only when cwd is that branch's canonical linked worktree. This mode blocks on tracked or staged edits, requires main integration, and preserves all untracked local content through the recoverable archive transaction before worktree removal.
- Use `--stable-checkout` when cwd is exactly the canonical stable checkout. This is thread-scoped closeout: preserve the stable checkout directory and every local file, skip branch/integration checks, skip worktree and local-content archival/removal, and skip archive-directory purging. Never select or remove an unrelated `ws/*` worktree merely because one exists.

The two target selectors are mutually exclusive. Do not invent a branch to make stable-checkout finish pass task-worktree validation.

An explicit finish prompt submitted while the thread was in Plan mode must arrive
with the global hook's verified Default-mode developer context. Continue cleanup in
that same turn without calling `finish-handoff` or queueing another `$task finish`.
If Plan instructions are still active, stop before cleanup and report the hook
installation, trust, App Server control, or prompt-recognition failure. Do not tell
the user to switch modes manually and do not ask the Plan-mode Agent to perform the
transition.

Read and follow [references/finish.md](references/finish.md). Run `task-lifecycle-control finish-cleanup` with the exact stable repo and applicable target selector. A task document is optional and never gates cleanup; finish must not create a missing one. Do not reproduce the script's local-content archival, cc-connect CAS unbind, worktree removal, or stable-checkout preservation logic manually.

Read `closeThreadId` and `closeSessionKey` from `finish-cleanup`. Prepare the final response, then run `task-lifecycle-control finish-close` with the same target selector and `--thread-id <closeThreadId>` as the final tool operation when that value is non-empty; omit `--thread-id` only when task-worktree cleanup returned `null`. In stable-checkout mode, also pass `--session-key <closeSessionKey>` when cleanup returned one. The helper requires the active invoking persistent thread, refuses a changed cc-connect attachment, removes that Feishu group's Feed Shortcut when present, and archives only that thread. The helper defers archival when the finishing turn remains active. After this command, perform no more tool, filesystem, document, or messaging operation.

## Failure handling

After an interrupted or uncertain write, inspect before retrying. Outside the exact cleanup authorized by explicit `finish`, do not automatically delete, roll back, rename, move, or overwrite existing branches, worktrees, groups, bindings, sessions, documents, shortcuts, or messages. Preserve completed phases and report the exact recovery point.
